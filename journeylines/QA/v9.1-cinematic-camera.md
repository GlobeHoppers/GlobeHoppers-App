# GlobeHoppers v9.1 — Cinematic Motion Camera

**Feature branch:** `feature/v9-cinematic-camera`, based on v9 production `407f32e5`. This update does not change `main`, traveler records, Studio saves, routing, playback timing, or GPU budgets.

## Behavior

- **Cinematic** is the default motion profile on this feature branch. **Classic** reproduces the prior v9 follow-camera path.
- Advanced Controls → **Camera motion** switches between Cinematic and Classic without rebuilding route geometry. The choice is saved in browser localStorage (`globehoppers.cameraMotion.v9`).
- `?v9Cinematic=0` forces a Classic load. `?v9Cinematic=1` forces Cinematic on initial load. The full `?v9Legacy=1` rescue URL remains respected.
- Cinematic motion affects **Follow camera mode** on the 3D globe. Route, continent, global and 2D map views keep their existing behavior. Screensaver hides the normal controls but uses the selected profile.

## Design

`src/utils/cinematicCamera.js` constructs a deterministic, read-only camera plan from 12 samples of the canonical `getScene` camera per leg, then interpolates with monotone cubic Hermite curves. Longitude and bearing are unwrapped across the dateline.

The plan adds limited lead, a departure push-in, widening during cruise, an approach zoom, and pitch/bearing choreography tied to travel mode and direction. All changes are bounded; pitch is limited to 75°, and the vehicle and trail positions are untouched.

The existing v9 `PlaybackEngine` remains **the only animation clock**, and the existing WP3 renderer remains the only MapLibre camera owner. No additional RAF, timers, React per-frame render, routing worker, or camera animation API was introduced.

A connected-leg transition anchors the next spline to the actual rendered camera when the next leg starts. Disconnected legs keep their existing dedicated relocation glide. A live profile change blends over 850 ms; a seek jumps deliberately to its exact location on the deterministic cinematic plan. Manual camera gestures continue to override playback and use the existing controlled camera-return path.

## Validation / risks

- `node --test scripts/test-v9-cinematic-camera.mjs`: camera plan created only once; deterministic sampling; zoom/pitch/bank bounds; no longitude/bearing wrap; connected-leg no-cut start; manual profile blend; rescue flags.
- Core v9 clock/renderer/transition and source-data parity tests still run in CI on this feature branch.
- Chromium viewer smoke exercises an actual playing cinematic route, confirms the camera plan is active, switches Classic/Cinematic, and opens/closes Studio without loading canonical route data prematurely.
- Four-way software Chromium benchmark explicitly forces Classic to keep its original meaning. Cinematic visual quality must be judged in real hardware; headless SwiftShader cannot measure physical smoothness.
- Do not claim production parity or change `main` until browser and feature QA pass. Manual visual checks should include connected return flights, disconnected relocation, mid-flight seek, manual globe spin/reacquisition, long-haul dateline routes, car/boat/train surface geometry, and a screensaver cycle.

## Architectural boundary

This update only changes camera choreography. It does **not** retime the plane/vehicle or route reveal. The deliberate departure/arrival camera moves should improve visual energy without corrupting progress. A future global story-mode pacing system is a separate design decision, not part of this work package.
